# ZK-LoRaWAN Backend Production Deployment Checklist

This checklist outlines the remaining operational, cryptographic, and security requirements to transition ZK-LoRaWAN from a devnet/field-trial sandbox to a mainnet-ready, high-assurance production environment.

---

## 1. Solana Smart Contract (On-Chain) Hardening

### Multi-Sig & Upgrade Governance
- [ ] **Squads V4 Multisig Integration:** Upgrade program upgrade authority from a single hot developer key to a multi-sig PDA governed by at least 3-of-5 trusted signatories.
- [ ] **Fee Configuration Governance:** Bind parameters like `GATEWAY_REWARD_LAMPORTS` and `PROTOCOL_FEE_LAMPORTS` to multi-sig settings updates instead of hardcoded constants.

### Economic Security & Circuit Protection
- [ ] **Gateway Claim Rate-Limiting:** Implement an on-chain daily claim limit cap per gateway to prevent rapid draining of the escrow pool in the event of a zero-knowledge circuit soundness exploit.
- [ ] **Escrow Account Segregation:** Configure sub-vault accounting pools so that any compromise of a specific sub-tree does not compromise the entirety of the system's escrow reserves.
- [ ] **RF Signal Evidence Check (RSSI/SNR limits):** Implement on-chain or gateway-reputation range checks on RSSI/SNR signal levels. If a node claims to route packets but reports unrealistic perfect signals (e.g. constant 0dB SNR or -30dBm RSSI which only happens in zero-distance lab setups), flag it as a simulated loopback sybil attack and suspend payouts.

### Registry Administration
- [ ] **Firmware Hash Revocation Flow:** Implement an admin-invoked revocation instruction to immediately blacklist compromised or vulnerable firmware image hashes.
- [ ] **Registry Lifecycle Epochs:** Define epoch-based firmware signatures that expire periodically, prompting mandatory device updates.

### Code Auditing
- [ ] **Formal Verification:** Run mathematical verification of the Anchor program state machine using formal solvers (such as Certora or Veridise).
- [ ] **Professional Code Audit:** Complete a comprehensive third-party audit of the Solana program and associated FFI bindings.

---

## 2. Production Trusted Setup (Phase 2 MPC)

### MPC Infrastructure
- [ ] **Ceremony Coordinator Server:** Deploy a secure, containerized MPC coordinator backend (e.g., using SnarkJS or custom coordinate buffers) with DDOS protection.
- [ ] **Public Attestation Transcript:** Set up a public, read-only bucket (AWS S3 or IPFS) hosting the running ceremony transcripts and contribution parameters.
- [ ] **VK Upgrade State Transition:** Verify that the Solana program has a state-transition window allowing old VK and new VK to co-exist for exactly 1 epoch (e.g., 2–3 days) during upgrades, preventing instant disruption of active edge devices during key rotations.

### Contributor Coordination
- [ ] **Participant Onboarding:** Invite a diverse cohort of at least 10–20 reputable independent validators, developers, and community members to contribute entropy.
- [ ] **Algebraic Soundness Verification:** Ensure the final verifying key (`verifying_key.bin`) matches the deterministic output generated by hashing the complete ceremony transcript.
- [ ] **Verification CLI Release:** Distribute a public tool allowing any user to verify the algebraic transition proofs ($H$-query, $L$-query, $\delta$, and pairing constraints) for every contributor.

---

## 3. Gateway Daemon & Relayer Backend Production

### Transaction Signing & Key Management
- [ ] **KMS / Cloud HSM Integration:** Configure gateway daemons to request packet signatures via AWS KMS, GCP KMS, or a local Hardware Security Module (HSM), completely removing raw private keys from disk files.
- [ ] **Sub-Account Vault Funding:** Limit gateway transaction wallets to small operational margins ($\approx 1\text{–}2$ SOL) with automated refilling scripts to cap exposure if a gateway host is compromised.

### Replay Prevention & Mempool Filtering
- [ ] **High-Performance Nullifier Cache:** Configure a local, replicated **Redis** or **RocksDB** instance on the gateway. The daemon must query this cache to check nullifiers before submitting transaction batches to Solana, avoiding paying gas on replayed/failed proofs.
- [ ] **Pending Transaction Tracker:** Gateways must track pending mempool nullifiers in flight to prevent double-spending race conditions.

### RPC Operations & Dynamic Fees
- [ ] **Dynamic Priority Fee Calculation:** Implement a fee estimator using `getRecentPrioritizationFees` to dynamically set compute unit prices, ensuring transactions land on-chain during high Solana network congestion.
- [ ] **RPC Node Load Balancing:** Configure gateway clients with automatic failover across multiple dedicated RPC endpoints (e.g., Triton, QuickNode, Helius).
- [ ] **Jito MEV Bundles Integration:** Build transaction batches as Jito bundles to guarantee atomic execution of verification chunk sequences.

---

## 4. Edge Node Hardware Production

### Physical Microcontroller Fusing
- [ ] **Secure Boot V2 Fusing:** Enable and cryptographically fuse Secure Boot V2 on the ESP32 chipsets to prevent flashing modified firmware.
- [ ] **Hardware Flash Encryption:** Burn the flash encryption keys into the microcontroller's eFuses, preventing physical reading of private keys or binary code from the flash chip.

### ATECC608A Integration
- [ ] **Slot Configuration Locking:** Configure and permanently lock the ATECC608A data slots, writing the device private identity keys to read-protected, secure enclaves.
- [ ] **ZK Witness Attestation Binding:** Implement the cryptographic binding mapping the ATECC608A internal hardware ECDSA signature to the Groth16 witness inputs (`firmware_hash_witness`, `private_key` proof validation).

### Secure OTA Updates
- [ ] **Signed OTA Update Engine:** Implement a secure Over-The-Air (OTA) update pipeline where updates are decrypted and validated on-chip using keys stored inside the secure element before flashing.
